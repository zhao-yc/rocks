# 双内核最简刷新率对照

本任务只交付两个独立诊断应用，用来对比刷新率和滚动表现。两份包使用同一原生 Java 界面、同一离线长页、同一动画与计数器；不接入 Rocks 的 Compose 工具栏、模糊、扩展或浏览数据，不改变正式浏览器的内核。

两份均为 1.0-kernel-test / versionCode 1，使用已有固定开发签名，可以同时安装并与 Rocks 并存。Firefox 手机包只包含 ARM64，模拟器 x86_64 包单独构建，不作为手机包交付。Chromium 不捆绑 Chrome 应用，实际 WebView 提供者和版本在界面顶部显示。

## 怎么比较

1. 两个应用采用相同的系统刷新率与省电设置；系统若有按应用设置高刷的选项，请将两份测试应用设为相同。
2. 先打开默认“本地测试”页，等待约 5 秒，记录顶部“系统报告 Hz”和页面“rAF FPS / P95”。
3. 分别慢拖、快滑并观察松手后的惯性滚动，再测试“自动滚动”。暂停后可按“重新计数”重新采样。
4. 使用地址栏在两份应用打开同一 HTTP(S) 网站，比较实际滚动感受。两者均不主动申请固定 60/120Hz，不更改引擎帧率偏好或用户代理。

“系统报告”来自本应用 Display.getRefreshRate；rAF FPS 是网页回调频率的估算，P95 是本次采样中 95% 帧间隔的上界，不是实际合成呈现帧数或触摸延迟。60Hz 对应的理想间隔约 16.7ms，120Hz 约 8.3ms。系统 Hz 不同的结果需先考虑系统按应用分配的策略；系统 Hz 相同而计数或滚动表现不同，才进一步检查引擎与呈现过程。高刷手机上的结果尚待用户实测。

## 构建与实际验证（2026-11-01）

- 源码提交：1a02865；[任务分支完整构建](https://github.com/zhao-yc/rocks/actions/runs/41295378107) 与 [main 完整构建](https://github.com/zhao-yc/rocks/actions/runs/41295627243) 均通过。
- 运行命令：node --test scripts/test-kernel-comparison.mjs；gradle -p android/kernel-compare testChromiumDebugUnitTest testGeckoDebugUnitTest lintChromiumDebug lintGeckoDebug assembleChromiumDebug assembleGeckoDebug。计数器 4 项回归通过，两种变体分别 3 项 JVM 测试通过，lint 均为 0 错误、6 警告。
- 使用 CI 预装 JDK 17、Gradle 9.3.1、SDK 37/build-tools 36.0.0。显式禁止 SDK 自动下载，未安装 SDK、接受新许可或使用 Docker。CI 使用已有签名并在结束后清理临时私钥，本机没有生成或保存新私钥。
- CI 和下载后本地分别核对来源归档摘要、实际 APK v2 证书、包名及架构；两份手机包内 test-page.html、frame-meter.js 逐字节一致。
- 独立只读 Android 15 / API 35 x86_64 实例：系统 WebView 124.0.6367.219，显示报告 60Hz。Chromium 使用实际手机通用包，Firefox 使用同源码的独立 x86_64 包。没有操作其他任务模拟器。
- 最终两包的冷启动、非零视口、rAF 计数更新、自动滚动到后续段落、停止、手动滑动及刷新通过。原生打开、本地测试、后退、刷新控件的实际屏幕范围一致；不以模拟器波动的 FPS 评价手机内核性能。
- 连续滚动期间 UIAutomator 无法取得空闲快照，因此设备检查在停止滚动后重新采集 XML，禁止复用旧快照作为通过或失败依据。首次页面加载延后到原生视口布局完成，避免初始化零尺寸；没有通过增加截图采样或改变 Gecko 默认 SurfaceView 后端来处理。
- 本次未创建公开 Release。对照 APK 与摘要单独交付，真实手机高刷表现、不同厂商策略及网站兼容性仍需分别确认。
